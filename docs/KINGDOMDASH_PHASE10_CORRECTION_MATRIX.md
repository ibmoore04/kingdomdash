## 1. Master Architectural Correction Matrix

| # | Issue / Gap Identified | Original Initial Design | Mandated Architectural Correction | Final Authoritative Decision | Primary Documents Updated |
| :- | :--- | :--- | :--- | :--- | :--- |
| **1** | **State Machine Conflation** | Treated order and delivery lifecycles as a single blended state, assuming rider assignment acceptance meant delivery pickup. | Explicitly separate three distinct, non-interchangeable state machines: Order, Delivery, and Assignment. | Three discrete state machines formalized. `deliveries.status = 'assigned'` and `delivery_assignments.status = 'accepted'` coexist concurrently. Acceptance does not advance delivery to picked up. | `REQUIREMENTS.md` (§3)<br/>`DESIGN.md` (§1)<br/>`TASKS.md` (T1, T3) |
| **2** | **Generic Bidirectional Sync Trigger Risk** | Proposed `trg_fn_sync_delivery_to_order()` to mirror status updates automatically between tables. | Eliminate generic triggers completely to prevent recursive cascades, deadlocks, and unvalidated status jumps. | Generic triggers strictly banned. Replaced by atomic `SECURITY DEFINER` transition RPCs (`mark_delivery_picked_up`, `mark_delivery_in_transit`, `mark_delivery_delivered`, `cancel_order_operational`) updating both entities in one transaction. | `REQUIREMENTS.md` (§5)<br/>`DESIGN.md` (§2)<br/>`TASKS.md` (T3, T7) |
| **3** | **Payment Confirmation vs Fulfillment Boundary** | Ambiguity regarding whether payment confirmation means vendor accepted order or order is preparing. | Keep payment confirmation strictly distinct from merchant fulfillment operations. | Payment confirmation sets `orders.status = 'payment_confirmed'`. Order enters `preparing` only when vendor explicitly calls `update_order_status_vendor('preparing')`. | `REQUIREMENTS.md` (§4.1)<br/>`DESIGN.md` (§4)<br/>`TASKS.md` (T2, T4) |
| **4** | **Automatic Delivery Instantiation & Idempotency** | No automatic delivery creation upon payment, risking orphaned paid orders or duplicate delivery entries. | Enforce server-side, idempotent creation of exactly one delivery record upon payment confirmation. | Trigger `trg_create_delivery_on_payment_confirmed` fires on `orders.status = 'payment_confirmed'` with `IF NOT EXISTS` guard, freezing customer and pickup contact snapshots. | `REQUIREMENTS.md` (§4.1)<br/>`DESIGN.md` (§10)<br/>`TASKS.md` (T2) |
| **5** | **Immutability Terminology & Enforcement** | Described delivery snapshot immutability as "cryptographic immutability" without cryptographic mechanisms. | Replace with database-enforced immutability via role permission revocation. | Corrected to "database-enforced immutability". Direct `UPDATE` and `DELETE` on `orders` and `deliveries` tables revoked for `authenticated` role. Mutations restricted to secure RPCs. | `REQUIREMENTS.md` (§4.1)<br/>`DESIGN.md` (§8.1)<br/>`TASKS.md` (T1, T10) |
| **6** | **Dispatch Timing & Readiness Gate** | Ambiguity over whether rider assignment occurs during preparation or only after `ready_for_pickup`. | Explicitly define the dispatchable window and enforce pickup readiness rules. | Parallel dispatch permitted during `preparing` (enabling rider travel to store), but `mark_delivery_picked_up()` strictly requires `orders.status = 'ready_for_pickup'` for food/grocery. | `REQUIREMENTS.md` (§8.1)<br/>`DESIGN.md` (§5.1)<br/>`TASKS.md` (T5, T7) |
| **7** | **Assignment Acceptance & Rejection Omission** | Task breakdown omitted dedicated rider assignment response operations. | Implement standalone, dedicated RPCs for assignment acceptance and rejection. | Dedicated RPCs `accept_delivery_assignment` (sets assignment `accepted`, delivery stays `assigned`) and `reject_delivery_assignment` (sets assignment `rejected`, delivery reverts to `pending`). | `REQUIREMENTS.md` (§4.3)<br/>`DESIGN.md` (§4, §9)<br/>`TASKS.md` (T6) |
| **8** | **Courier Order Ingestion Gap** | `create_order_secure` explicitly rejects courier orders; courier lacked an authoritative ingestion path. | Provide an authoritative server-side pathway for creating and pricing courier dispatch orders. | Dedicated RPC `create_courier_order_secure` introduced. Sets `vendor_id = NULL`, computes distance pricing, skips vendor prep stages, and enters dispatch immediately upon payment. | `REQUIREMENTS.md` (§7.2)<br/>`DESIGN.md` (§6)<br/>`TASKS.md` (T9) |
| **9** | **Cancellation Authority & Refund Boundary** | Unrestricted cancellation rules with potential to falsely represent refunds as completed. | Enforce role-based cancellation gates; record `refund_required = TRUE` without claiming refund execution. | Explicit cancellation matrix: Customer (pre-payment only), Vendor (pre-prep only), Admin (pre-delivery). Paid cancellations set `refund_required = TRUE` and `refund_status = 'pending_manual_review'`. | `REQUIREMENTS.md` (§6)<br/>`DESIGN.md` (§7)<br/>`TASKS.md` (T8) |
| **10** | **Vendor Tenant Isolation & Commercial Truth** | Risk of vendors updating orders of other stores or altering items, quantities, or prices. | Enforce server-side ownership verification and eliminate commercial parameters from vendor RPCs. | Vendor identity cryptographically verified via `vendors.profile_id = auth.uid()`. Vendor RPCs accept zero financial/item arguments; direct table updates revoked. | `REQUIREMENTS.md` (§4.2, §9)<br/>`DESIGN.md` (§8.2)<br/>`TASKS.md` (T4, T10) |
| **11** | **Rider Eligibility & Concurrency Defenses** | Relied on client-reported availability; potential for duplicate active rider assignments. | Server-enforced eligibility and database constraints preventing concurrent in-flight deliveries. | `assign_delivery_to_rider` verifies `is_verified`, `is_active`, `is_available`, and 0 active tasks with `SELECT ... FOR UPDATE`. Partial unique index `idx_active_delivery_assignment` created. | `REQUIREMENTS.md` (§8.2)<br/>`DESIGN.md` (§5.2)<br/>`TASKS.md` (T1, T5) |
| **12** | **PostgreSQL Error Semantics** | Design documents referenced HTTP 403 and HTTP 409 inside database stored functions. | Database functions must raise structured exceptions with SQLSTATE error codes. | All PostgreSQL RPC specifications updated to raise standard SQLSTATE codes: `KD400` (Bad Request), `KD403` (Forbidden), `KD404` (Not Found), `KD409` (Conflict). | `REQUIREMENTS.md` (§8.1)<br/>`DESIGN.md` (§4)<br/>`TASKS.md` (T3) |
| **13** | **Trusted Audit Metadata** | Audit logging accepted `client_ip` and `user_agent` from caller payloads. | Metadata must be derived strictly from trusted server context. | RPCs extract client IP and user agent via `current_setting('request.headers', true)::json`. Caller-supplied metadata arguments removed. | `REQUIREMENTS.md` (§9)<br/>`DESIGN.md` (§8.3)<br/>`TASKS.md` (T11) |
| **14** | **Customer Tracking Privacy & State Derivation** | Risk of exposing private rider data or fabricating progress stages in client state. | Restrict customer data disclosure and derive timeline exclusively from authoritative database status. | Customer tracking exposes only assigned rider first name, vehicle type, and phone number via authenticated order relation. Progress timeline derives strictly from server order status. | `REQUIREMENTS.md` (§7, §9)<br/>`DESIGN.md` (§8)<br/>`TASKS.md` (T12) |
| **15** | **Implementation Task Structure** | Initial 14-task graph lacked dedicated tasks for acceptance/rejection, courier ingestion, and atomic RPC engine. | Restructure implementation sequence into 15 granular, dependent, verifiable tasks. | Authoritative 15-task sequence established: T1 (Schema/Timestamps) through T15 (E2E Validation). Full dependencies mapped. | `TASKS.md` (§1, §2) |
