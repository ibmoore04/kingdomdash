## 1. Executive Summary & Objective

The objective of **Phase 13 — Notifications & Supporting Systems** is to implement, harden, and unify the platform-wide event-driven communication and notification infrastructure for KingdomDash.

KingdomDash serves three distinct services:
1. **Food Delivery** (Restaurant meals, kitchen preparation, courier dispatch)
2. **Grocery Delivery** (Supermarket goods, merchant packing, courier dispatch)
3. **Courier Dispatch** (Direct peer-to-peer and business parcel transport)

Following the completion of the commercial ordering engine (Phase 6), Paystack payment verification (Phase 9), three-tier operational state machine (Phase 10), Rider Platform (Phase 11), and Admin Control Center (Phase 12), Phase 13 establishes the authoritative bridge between database-level business transitions and human actors across all four roles: **Customers**, **Vendors**, **Riders**, and **Administrators**.

### Cardinal Architectural Axioms:
1. **Backend Event-Driven Authority:**  
   Notifications must be generated by authoritative server-side events (PostgreSQL triggers and SECURITY DEFINER RPCs), never solely from transient frontend client states.
2. **Deterministic Idempotency Protection:**  
   Every event notification must have a deterministic idempotency key. Network retries, webhook repetitions, database trigger replays, and UI re-renders must never produce duplicate notifications.
3. **Universal Recipient Identity:**  
   Recipient identity is grounded strictly in `public.profiles.id`. No parallel or disconnected user identity systems shall be introduced.
4. **Separation of Severity vs. Category:**  
   Visual alert styling (`type`: `info`, `success`, `warning`, `error`) is decoupled from business domain classification (`category`: `order`, `delivery`, `payment`, `application`, `system`, `promotional`).
5. **Enforceable User Preferences with Transactional Protection:**  
   Non-essential alerts respect user notification preferences, but critical operational and financial notifications (`payment_confirmed`, `in_transit`, `cancelled`) are mandatory and cannot be disabled.
6. **Zero Client Mutation Access to Notifications:**  
   Direct `INSERT` and `UPDATE` access to `public.notifications` is restricted. Mutations are mediated through audited, row-level-isolated SECURITY DEFINER RPCs (`mark_notification_read`, `mark_all_notifications_read`, `clear_read_notifications`).

## 3. Notification Failure Semantics & Error Classification

Notification generation must never silently swallow infrastructure failures, nor allow safe idempotency retries to abort commercial orders.

### 3.1 Failure Classification
1. **Expected / Idempotent Conflicts**:
   - Condition: `(profile_id, idempotency_key)` violation.
   - Action: `ON CONFLICT (profile_id, idempotency_key) DO NOTHING`.
   - Result: Idempotent success (0 rows inserted, no error thrown, transaction proceeds).
2. **Unexpected Infrastructure / Database Failures**:
   - Condition: Missing foreign key, RLS violation, storage limit, or trigger exception.
   - Action: Trapped in trigger exception block; invokes `public.log_operational_audit_event('notification_emission_failed', ...)` with detailed context.
   - Result: Observable in forensic audit logs (`public.audit_logs`) while allowing critical operational transactions (e.g. order delivery completion) to complete successfully.

## 4. User Preference Hierarchy & Policy

Preferences are stored in `public.notification_preferences`:
```sql
CREATE TABLE public.notification_preferences (
  profile_id uuid PRIMARY KEY REFERENCES public.profiles(id) ON DELETE CASCADE,
  order_updates boolean NOT NULL DEFAULT true,
  delivery_updates boolean NOT NULL DEFAULT true,
  payment_updates boolean NOT NULL DEFAULT true,
  promotional boolean NOT NULL DEFAULT false,
  operational_alerts boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

### Preference Policy Rules:
1. **Mandatory Overrides**: If a notification event is designated **Mandatory**, `emit_notification()` bypasses preference checks and forces insertion.
2. **Configurable Opt-Outs**: For non-mandatory events:
   - Category `order` checks `order_updates`.
   - Category `delivery` checks `delivery_updates`.
   - Category `payment` checks `payment_updates`.
   - Category `promotional` checks `promotional` (default `false`).
   - Category `system` checks `operational_alerts`.
3. If no record exists in `public.notification_preferences`, defaults are assumed (`true` for operational, `false` for promotional).

## 5. Security & Isolation Model

1. **Row Level Security**:
   - `SELECT`: `profile_id = auth.uid()` or caller is admin/super_admin.
   - `INSERT`: Strictly revoked from normal users. Allowed only via `SECURITY DEFINER` trigger functions or admin role.
   - `UPDATE`: Revoked from all users. Handled strictly through `mark_notification_read(uuid)` and `mark_all_notifications_read()`.
   - `DELETE`: Permitted only for caller's own **read** notifications: `profile_id = auth.uid() AND is_read = true`.
2. **Payload Protection**:
   - Notification `metadata` must contain only entity references (`order_id`, `delivery_id`, `vendor_id`). Never store Paystack secret keys, auth tokens, or card credentials.
3. **Realtime Isolation**:
   - Channel: `realtime:notifications:${auth.uid()}`.
   - Filtering: Client-side filter `profile_id=eq.${auth.uid()}` backed by Supabase RLS and `REPLICA IDENTITY FULL`.
